# 季節の常識（今日は何の日）設計案 v0.1

新方向「習慣の理由をアプリの外が供給する仕組み」（2026-11-27 本人決定、全プロジェクト共通テーマ）の
オトナレベル100 での具体化。2026-11-27 に本人が「この設計で実装する」と承認し、v0.15.0 で実装済み
（Seasonal.kt＋季節問題24問＋ホームの暦カード＋デイリーの季節枠＋問題画面の「季節」タグ）。

## 共通の思想・意図（全プロジェクト共通、2026-11-27 本人提示）

1. **理由は作らない、外にあるものに乗る**：通知で煽る・ストリークで縛るなど、アプリの中で理由を
   製造しない。暦・天気・他人の予定・身体のリズム・お金の暦など、世の中で既に回っている理由に
   アプリが「乗る」。アプリは理由の製造者ではなく、理由と人を繋ぐ受け皿。
2. **盛らない・煽らない**：外の理由は日付や天気という事実なので嘘も水増しもできない。そこが信頼に
   直結する。演出で盛らず、事実を静かに届ける。
3. **途切れても責めない**：ストリークや連続記録で縛らない。途切れは失敗ではなく、「戻ってきた」が
   一番のイベント。復帰を祝う。罪悪感で続けさせる設計は禁止。
4. **成功の定義**：毎日開かせることではなく、「必要な日に、ちょうど届くこと」。開かれない日があって
   よい。習慣化して卒業されることも敵とせず、「区切りに戻ってくる場所」まで含めて設計する。
5. **宗教そのものは扱わない**：借りるのは「外が理由を供給する」という構造だけ。
6. **マネタイズは理由の供給とセットで考える**（シーズンパス、失効・期限の静かなお知らせなど）。
   煽って売らない。

## このアプリでの設計

- 暦イベント表を端末内に持つ（通信なし）。固定日と「第○月曜」等の浮動日を計算で出す。
  イベント = { id, 名前, 期間, 一言（事実のみ・目安は「目安」と明記）, 問題セット }。
- 期間中だけホームに「今日は何の日」カードを表示。期間が終わればカードごと消える（成功の定義4：
  必要な日にだけ届く）。
- 問題の出し方：期間中はデイリーの新規枠3問のうち1問を季節問題に差し替える（復習枠は不変）。
  問題画面に「季節」タグ。季節問題も通常の復習サイクルに乗る。
- 文案ルール（思想2）：カードの文は事実と目安だけ。煽り・水増し表現を書かない。
- Phase 1 の行事（直近3か月で効く順）：お歳暮／年末年始／成人の日／節分／確定申告／ひな祭り、各4問。
- Phase 2：お中元／お盆／敬老の日／七五三など年間分。シーズンパスは形ができてから（思想6）。

## 既存設計との整合

- 「レベルは絶対に下がらない／ストリークで責めない」は思想3と元から一致。
- 通知は本アプリに存在しない（思想1・2と一致。今後も煽る通知は足さない）。
